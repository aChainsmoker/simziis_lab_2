# Отчёт о разработке и анализе безопасности приложения

## 1. Общие сведения

Разработано веб-приложение для регистрации и авторизации пользователей, а также создания, редактирования, удаления и поиска конфиденциальных и неконфиденциальных данных.

Backend реализован на Python с использованием FastAPI и SQLite. Frontend реализован с использованием HTML, CSS и JavaScript.

Основные технологии:

- FastAPI — HTTP API и маршрутизация;
- SQLAlchemy — взаимодействие с базой данных;
- SQLite — хранение данных;
- bcrypt — хэширование паролей;
- JWT — access-токены;
- Fernet — шифрование конфиденциальных данных;
- `python-dotenv` — загрузка конфигурации из `.env`.

## 2. Реализованные функции

Приложение предоставляет следующие возможности:

1. Регистрация пользователя.
2. Автоматическая авторизация после регистрации.
3. Вход по имени пользователя и паролю.
4. Хранение пароля только в виде bcrypt-хэша.
5. Хранение access-токена в HttpOnly cookie.
6. Автоматическая передача cookie браузером с защищёнными запросами.
7. Выход пользователя и отзыв текущего токена.
8. Создание, редактирование, удаление и поиск конфиденциальных данных.
9. Создание, редактирование, удаление и поиск неконфиденциальных данных.
10. Разделение данных в интерфейсе на две вкладки.

## 3. Архитектура приложения

Приложение разделено на слои:

```text
domain          сущности предметной области
repositories    операции чтения и записи в БД
services        бизнес-логика
infrastructure  БД, модели, хэширование, токены и шифрование
api             HTTP-эндпоинты и зависимости авторизации
frontend        пользовательский интерфейс
```

Такое разделение снижает связанность компонентов. API не работает с базой напрямую: запрос проходит через сервис и репозиторий. Средства шифрования, хэширования и работы с JWT изолированы в инфраструктурном слое.

## 4. Анализ политики безопасности операционной системы

### 4.1. Защищаемые ресурсы

К ресурсам операционной системы относятся:

- файл базы данных `lab2.db`;
- файл `.env` с секретным ключом шифрования и JWT-секретом;
- исходный код приложения;
- виртуальное окружение Python;
- сетевой порт, на котором работает Uvicorn.

### 4.2. Требования к ОС

Процесс приложения должен запускаться от обычной учётной записи без прав администратора. Это ограничивает последствия возможной компрометации приложения.

Доступ к каталогу `lab2` должен быть разрешён только владельцу приложения и учётной записи, от которой запускается сервер. Особенно важно ограничить доступ к следующим файлам:

- `.env`;
- `lab2.db`;
- исходным файлам приложения.

Файл `.env` не должен передаваться в систему контроля версий. Для этого он должен быть добавлен в `.gitignore`.

Операционная система должна своевременно обновляться, а зависимости Python — устанавливаться из фиксированного и проверенного списка. Сервер следует запускать в виртуальном окружении.

### 4.3. Возможные угрозы

- чтение `.env` другим пользователем ОС;
- копирование файла SQLite;
- изменение исходного кода или базы данных;
- запуск приложения с избыточными правами;
- использование уязвимых версий Python-пакетов.

### 4.4. Меры защиты

- ограничение прав на каталог проекта;
- запуск без прав администратора;
- хранение секретов вне исходного кода;
- резервное копирование базы данных с ограничением доступа;
- регулярное обновление зависимостей;
- использование отдельной учётной записи для production-сервера.

## 5. Анализ безопасности компонентов и их взаимодействия

### 5.1. API-слой

API принимает запросы от frontend и передаёт их в сервисный слой. Защищённые маршруты используют зависимость `current_user`, которая:

1. извлекает Bearer-токен;
2. проверяет, не был ли токен отозван;
3. проверяет подпись и срок действия JWT;
4. получает пользователя из базы данных.

Основной риск API — отсутствие полноценного ограничения частоты запросов. Это может позволить выполнять большое количество попыток входа или поиска.

### 5.2. Сервисный слой

Сервисы проверяют бизнес-права пользователя. Для конфиденциальных записей пользователь может получить, изменить или удалить только собственные записи.

Сервисный слой не должен доверять идентификатору пользователя, переданному клиентом. В текущем приложении идентификатор берётся из проверенного токена, что предотвращает подмену владельца.

### 5.3. Репозитории

Репозитории инкапсулируют запросы SQLAlchemy. Использование ORM снижает риск ручных SQL-инъекций. Параметры поиска передаются средствами SQLAlchemy.

Для конфиденциальных данных репозиторий расшифровывает содержимое после получения из БД. Поэтому поиск по содержимому выполняется в памяти приложения, а не с помощью SQL-запроса.

### 5.4. Инфраструктурный слой

Пароли обрабатываются bcrypt. Это одностороннее хэширование с солью: исходный пароль не хранится и не восстанавливается.

JWT подписывается секретным ключом. Секрет должен храниться в `.env`, а не в исходном коде.

Конфиденциальные данные шифруются Fernet перед записью в SQLite. Ключ шифрования должен храниться отдельно от базы данных. Потеря ключа приведёт к невозможности расшифровать данные.

### 5.5. Frontend

Frontend не имеет доступа к access-токену: токен хранится в HttpOnly cookie и автоматически отправляется браузером.

Это снижает риск кражи токена через XSS. Для production также необходимы флаги `Secure` при работе по HTTPS и CSRF-защита.

## 6. Анализ сетевой политики безопасности

### 6.1. Текущая модель

Frontend и API обслуживаются одним FastAPI-приложением. В разработке приложение запускается через Uvicorn и доступно по HTTP, обычно на локальном порту `8000`.

Для CORS разрешены только конкретные локальные origins: `http://127.0.0.1:8000` и `http://localhost:8000`.

### 6.2. Основные угрозы

- перехват JWT при использовании обычного HTTP;
- подбор пароля большим количеством запросов;
- подмена или повторное использование токена;
- неправильная настройка разрешённых origins;
- раскрытие технической информации через ошибки;
- отсутствие reverse proxy и сетевого фильтра.

### 6.3. Рекомендации

- использовать HTTPS;
- поддерживать список разрешённых origins в конфигурации;
- добавить rate limiting для регистрации и входа;
- закрыть порт приложения от внешнего доступа, если приложение локальное;
- использовать Nginx или другой reverse proxy;
- не передавать секреты и токены в URL;
- включить журналирование важных событий безопасности.

## 7. Анализ безопасности конфиденциальности данных

### 7.1. Пароли

Пароли не сохраняются в исходном виде. При регистрации пароль хэшируется bcrypt. При входе введённый пароль сравнивается с сохранённым хэшем.

Таким образом, утечка таблицы пользователей не должна позволить сразу получить исходные пароли. Пользователь всё равно должен использовать уникальный пароль.

### 7.2. Конфиденциальные данные

Содержимое конфиденциальных записей шифруется перед сохранением в SQLite. В базе находятся зашифрованные значения, которые невозможно прочитать без ключа Fernet.

При поиске приложение:

1. получает конфиденциальные записи текущего пользователя;
2. расшифровывает их внутри backend;
3. выполняет поиск в памяти;
4. возвращает только подходящие записи.

База данных не выполняет `LIKE` по зашифрованному содержимому, поскольку зашифрованный текст не сохраняет исходные слова.

### 7.3. Разграничение доступа

Конфиденциальные записи связаны с `user_id`. Пользователь не может изменять или удалять запись другого пользователя.

Неконфиденциальные записи доступны авторизованным пользователям для просмотра и поиска, однако редактирование и удаление разрешено только автору записи.

### 7.4. Риски

- ключ шифрования находится на том же сервере, что и приложение;
- при компрометации backend ключ может быть прочитан процессом приложения;
- cookie-токен требует CSRF-защиты при расширении приложения;
- поиск по конфиденциальным данным требует загрузки данных текущего пользователя в память;
- SQLite не предназначен для параллельной высоконагруженной работы;
- при использовании старых записей, созданных до включения шифрования, требуется отдельное шифрование этих записей.

## 8. Основные выявленные риски и приоритеты исправления

| Риск | Уровень | Рекомендация |
|---|---:|---|
| HTTP вместо HTTPS | Высокий | Использовать TLS и reverse proxy |
| Cookie-токен без CSRF-защиты | Средний | Добавить CSRF-токены для production |
| Ошибка в списке CORS origins | Средний | Поддерживать только доверенные origins |
| Нет ограничения частоты запросов | Средний | Добавить rate limiting |
| Ключ шифрования на сервере приложения | Средний | Использовать secrets manager или защищённое хранилище |
| SQLite для production-нагрузки | Средний | Перейти на PostgreSQL |
| Поиск расшифровывает записи в памяти | Низкий/средний | Добавить пагинацию или отдельный поисковый индекс |

## 9. Итоговый вывод

Приложение реализует основные требования задания и содержит базовые меры защиты: разделение слоёв, проверку JWT, bcrypt-хэширование паролей, разграничение доступа к записям и шифрование конфиденциального содержимого.

Текущая реализация подходит для учебного приложения и локального использования. Для промышленной эксплуатации необходимо дополнительно использовать HTTPS, строгую CORS-политику, защищённое хранение токенов и ключей, ограничение частоты запросов, централизованное журналирование и более подходящую промышленную СУБД.
