# Отчёт о разработке и анализе защищённости приложения

## 1. Постановка задачи

Необходимо разработать приложение, которое позволяет:

- добавлять пользователей в систему;
- авторизовывать пользователей на основе идентификационных данных;
- создавать, редактировать, удалять и искать конфиденциальные данные;
- создавать, редактировать, удалять и искать неконфиденциальные данные;
- деавторизовывать авторизованного пользователя.

Приложение должно иметь многоуровневую архитектуру. Для реализации необходимо выделить следующие слои:

- слой домена — сущности приложения;
- слой репозиториев — взаимодействие с базой данных;
- слой сервисов — бизнес-логика;
- инфраструктурный слой — база данных, хэширование, шифрование и работа с токенами;
- слой API — HTTP-эндпоинты;
- пользовательский интерфейс — HTML, CSS и JavaScript.

Отдельным требованием является обеспечение защиты паролей и конфиденциальных данных, а также анализ приложения с точки зрения политики безопасности операционной системы, безопасности компонентов приложения и их взаимодействия, сетевой политики безопасности и безопасности конфиденциальной информации.

## 2. Краткое описание разработанного приложения

Приложение разработано на Python с использованием FastAPI. В качестве базы данных используется PostgreSQL, развёрнутый в Docker-контейнере, а для работы с ним — SQLAlchemy. Пользовательский интерфейс реализован на HTML, CSS и JavaScript и обслуживается тем же FastAPI-приложением.

### 2.1. Архитектура приложения

Проект разделён на следующие слои:

```text
lab2/
├── app/
│   ├── domain/          сущности предметной области
│   ├── repositories/    работа с базой данных
│   ├── services/        бизнес-логика
│   ├── infrastructure/  БД, JWT, bcrypt и шифрование
│   └── api/             HTTP-маршруты и авторизация
└── frontend/            HTML, CSS и JavaScript
```

Слой API принимает запросы клиента и передаёт их сервисам. Сервисы реализуют бизнес-правила и обращаются к репозиториям. Репозитории выполняют операции с базой данных. Инфраструктурный слой предоставляет внешние механизмы: PostgreSQL, bcrypt, JWT и Fernet.

### 2.2. Реализованные функции

В приложении реализованы:

1. Регистрация пользователя.
2. Автоматическая авторизация после регистрации.
3. Вход пользователя по имени и паролю.
4. Выход пользователя из системы.
5. Хэширование паролей с помощью bcrypt.
6. Создание, редактирование, удаление и поиск конфиденциальных данных.
7. Создание, редактирование, удаление и поиск неконфиденциальных данных.
8. Разделение данных в интерфейсе на две вкладки.
9. Отдельная страница создания и редактирования записей.
10. Шифрование конфиденциального содержимого перед сохранением в БД.

### 2.3. Авторизация

После успешной регистрации или входа сервер создаёт JWT access-токен и устанавливает его в HttpOnly cookie. JavaScript не имеет доступа к содержимому cookie, а браузер автоматически отправляет её с запросами к приложению.

При выходе токен удаляется из cookie и добавляется в список отозванных токенов. Защищённые эндпоинты проверяют наличие cookie, подпись, срок действия и факт отзыва токена.

## 3. Анализ защищённости приложения

### 3.1. Политика безопасности операционной системы

К защищаемым ресурсам операционной системы относятся:

- PostgreSQL-контейнер и его постоянный Docker volume;
- файл `.env`, содержащий секрет JWT и ключ шифрования;
- исходный код приложения;
- виртуальное окружение Python;
- сетевой порт FastAPI-приложения.

Приложение должно запускаться от обычной учётной записи без административных прав. Это уменьшает возможный ущерб при компрометации процесса. Доступ к каталогу `lab2` должен быть ограничен владельцем проекта и пользователем, под которым запускается сервер.

Особенно важно ограничить права на `.env`, Docker-конфигурацию и PostgreSQL volume. Файл `.env` исключён из системы контроля версий через `.gitignore`, поэтому секреты не должны попадать в репозиторий.

Рекомендуемая политика ОС:

- использовать актуальные версии операционной системы и Python;
- запускать приложение в виртуальном окружении;
- не запускать Uvicorn от имени администратора;
- ограничить права чтения и записи каталога приложения;
- выполнять резервное копирование базы данных в защищённое хранилище;
- регулярно обновлять зависимости и проверять их на уязвимости.

Основные угрозы на уровне ОС — чтение `.env` другим пользователем, доступ к Docker volume, изменение исходного кода и запуск контейнеров с избыточными правами.

### 3.2. Политика безопасности компонентов и их взаимодействия

Разделение на слои ограничивает прямой доступ компонентов друг к другу:

- API не выполняет SQL-запросы напрямую;
- сервисы отвечают за бизнес-правила;
- репозитории отвечают только за доступ к данным;
- инфраструктурные функции скрывают детали хэширования, токенов и шифрования;
- доменные сущности не зависят от HTTP и конкретной СУБД.

Такое разделение уменьшает связанность компонентов и облегчает контроль безопасности.

#### API-слой

Защищённые эндпоинты используют зависимость получения текущего пользователя. Она проверяет:

1. наличие access-токена в HttpOnly cookie;
2. наличие токена в списке отозванных токенов;
3. подпись и срок действия JWT;
4. существование пользователя в базе данных.

#### Сервисный слой

Сервисы проверяют права владельца записи. Пользователь может изменять и удалять только собственные записи. Идентификатор пользователя берётся из проверенного токена, а не из данных, переданных клиентом.

#### Репозитории

Репозитории используют SQLAlchemy. Это снижает риск SQL-инъекций по сравнению с формированием SQL-запросов через конкатенацию строк.

#### Инфраструктурный слой

Пароли обрабатываются bcrypt. JWT подписывается секретным ключом. Конфиденциальное содержимое шифруется Fernet перед сохранением в базу данных.

Основные недостатки текущей реализации:

- список отозванных токенов хранится в памяти и очищается при перезапуске приложения;
- отдельная защита от перебора паролей и ограничение частоты запросов не реализованы;
- для production требуется централизованное журналирование событий безопасности;
- необходимо добавить CSRF-защиту при использовании cookie в полноценной внешней среде.

### 3.3. Сетевая политика безопасности

В разработанном приложении frontend и API обслуживаются одним сервером, поэтому при обычном запуске используются один origin и один сетевой порт. CORS ограничен конкретными локальными адресами:

```text
http://127.0.0.1:8000
http://localhost:8000
```

Использование конкретного списка origins безопаснее, чем разрешение всех источников через `*`. При этом для production список должен содержать только фактический адрес frontend.

Основные сетевые угрозы:

- перехват cookie и запросов при использовании обычного HTTP;
- подбор пароля большим числом запросов;
- эксплуатация ошибок конфигурации CORS;
- повторное использование украденного токена;
- раскрытие информации через слишком подробные сообщения об ошибках.

Для повышения сетевой безопасности необходимо:

- использовать HTTPS;
- включить флаг `Secure` для cookie при работе через HTTPS;
- добавить CSRF-токены;
- реализовать rate limiting для регистрации и входа;
- использовать reverse proxy, например Nginx;
- закрыть порт приложения от внешнего доступа, если приложение используется локально;
- вести журнал входов, выходов и неуспешных попыток авторизации.

### 3.4. Общая оценка защищённости

Для учебного приложения реализован базовый набор механизмов защиты:

- пароли не хранятся в открытом виде;
- доступ к защищённым маршрутам требует авторизации;
- записи связаны с владельцами;
- токен недоступен JavaScript благодаря HttpOnly cookie;
- CORS ограничен доверенными адресами;
- конфиденциальные данные шифруются.

Приложение не следует считать полностью готовым к промышленной эксплуатации без HTTPS, защиты от CSRF, ограничения частоты запросов, централизованного хранения секретов и внешней СУБД.

## 4. Анализ защищённости конфиденциальной информации

### 4.1. Классификация данных

В приложении выделены два типа данных:

- конфиденциальные данные — доступны только владельцу;
- неконфиденциальные данные — доступны авторизованным пользователям для просмотра и поиска, но изменять и удалять их может только автор.

Для этих типов используются отдельные таблицы PostgreSQL: `confidential_data` и `public_data`.

### 4.2. Защита паролей

Пароль пользователя хэшируется алгоритмом bcrypt. В базе хранится только результат хэширования. При входе введённый пароль проверяется с помощью bcrypt, а исходный пароль не восстанавливается.

Таким образом, bcrypt обеспечивает необратимое преобразование пароля и использует соль, что затрудняет применение заранее подготовленных таблиц хэшей.

### 4.3. Шифрование конфиденциальных данных

Перед сохранением содержимое конфиденциальной записи шифруется с помощью Fernet. В базе данных хранится зашифрованная строка, а ключ шифрования хранится в переменной окружения `CONFIDENTIAL_DATA_KEY`.

При чтении записи backend расшифровывает содержимое только после прохождения проверки прав доступа. Ключ не передаётся frontend и не хранится в cookie.

Ключ шифрования должен находиться отдельно от резервной копии PostgreSQL. Если злоумышленник получит только резервную копию базы, содержимое конфиденциальных полей прочитать нельзя. Если будут раскрыты и база, и ключ, шифрование не обеспечит защиту.

### 4.4. Поиск по конфиденциальным данным

Зашифрованное содержимое нельзя искать обычным SQL-оператором `LIKE`, так как шифротекст не сохраняет исходные слова. Поэтому текущий алгоритм поиска следующий:

1. из базы загружаются конфиденциальные записи текущего пользователя;
2. содержимое записей расшифровывается на backend;
3. поиск по названию и содержимому выполняется в памяти приложения;
4. клиенту возвращаются только найденные записи.

В базу не передаётся открытое содержимое запроса поиска. Недостаток подхода — при большом количестве записей увеличиваются расход памяти и время поиска. Для производственной системы следует добавить пагинацию или отдельный защищённый поисковый индекс.

### 4.5. Риски конфиденциальности

К основным рискам относятся:

- доступ процесса приложения к ключу шифрования;
- хранение PostgreSQL и backend в одной инфраструктуре без дополнительной сегментации;
- возможность утечки данных при ошибке авторизации или неправильной проверке владельца;
- хранение cookie без флага `Secure` в режиме локального HTTP;
- отсутствие полноценной защиты от CSRF;
- загрузка всех конфиденциальных записей пользователя в память при поиске.

Эти риски уменьшаются проверкой владельца записи, шифрованием Fernet, использованием HttpOnly cookie и ограничением CORS, но для production необходимы дополнительные меры.

## 5. Вывод

### 5.1. Семантическая составляющая

В ходе работы разработано приложение, реализующее заданную предметную область: регистрацию пользователей, авторизацию, деавторизацию, управление конфиденциальными и неконфиденциальными данными, а также поиск записей. Приложение построено по многоуровневой архитектуре, в которой доменные сущности, репозитории, сервисы, инфраструктура и API имеют отдельные зоны ответственности.

С точки зрения информационной безопасности реализованы следующие смысловые свойства системы:

- пользователь получает доступ к защищённым операциям только после авторизации;
- конфиденциальные записи отделены от неконфиденциальных;
- доступ к конфиденциальной информации ограничен владельцем;
- пароли защищены необратимым хэшированием;
- конфиденциальное содержимое защищено обратимым шифрованием;
- сетевое взаимодействие ограничено доверенными origins.

### 5.2. Прагматическая составляющая

Практическим результатом работы является функционирующее веб-приложение, которое можно запустить локально и использовать через браузер. Пользователь может зарегистрироваться, сразу попасть в свой аккаунт, работать с двумя категориями данных и выйти из системы.

Разработанная архитектура позволяет расширять приложение: добавить роли пользователей, подключить централизованное хранилище секретов, внедрить rate limiting, HTTPS, CSRF-защиту и полноценное журналирование.

Итоговая оценка: приложение соответствует поставленным учебным требованиям и содержит базовые механизмы защиты. Для использования в реальной информационной системе необходимо усилить сетевую защиту, управление ключами, защиту cookie, контроль доступа к файлам ОС и устойчивость к перебору паролей.
