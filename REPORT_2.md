# Отчёт о разработке методики и анализе защищённости предоставленной системы

## 1. Постановка задачи

Одной из задач анализа программных систем является оценка их защищённости. Для получения объективного результата необходимо использовать комплексный подход, рассматривая не только исходный код, но и физические устройства хранения данных, операционную систему, программное окружение, базы данных, библиотеки, веб-сервер, сетевые протоколы, взаимодействие компонентов и порядок эксплуатации системы.

В рамках работы необходимо:

1. Разработать методику оценки защищённости систем.
2. Выполнить анализ предоставленного приложения с позиций:
   - политики безопасности операционной системы;
   - политики безопасности компонентов приложения и их взаимодействия;
   - сетевой политики безопасности;
   - безопасности конфиденциальности данных.
3. Предложить комплекс мер по усовершенствованию приложения.
4. Предложить рекомендации по безопасному использованию приложения.
5. Оформить отчёт о проделанной работе.

Методика должна учитывать возможные атаки на отдельные компоненты и на систему в целом, включая SQL-инъекции, XSS, HTTP-атаки, подбор паролей, кражу токенов, ошибки разграничения доступа и атаки на доступность.

## 2. Краткое описание предоставленной системы

Предоставленная система представляет собой веб-приложение для регистрации и авторизации пользователей, а также для управления конфиденциальными и неконфиденциальными данными.

Backend реализован на Python с использованием FastAPI. Для хранения данных используется PostgreSQL, развёрнутый в Docker-контейнере, доступ к базе данных выполняется через SQLAlchemy. Frontend реализован на HTML, CSS и JavaScript и обслуживается FastAPI.

### 2.1. Функциональность системы

Система поддерживает:

- регистрацию пользователя;
- автоматическую авторизацию после регистрации;
- вход по имени пользователя и паролю;
- выход из системы;
- создание, редактирование, удаление и поиск конфиденциальных данных;
- создание, редактирование, удаление и поиск неконфиденциальных данных;
- разделение данных на две вкладки;
- отдельную страницу создания и редактирования записи.

Конфиденциальные записи доступны только их владельцу. Неконфиденциальные записи доступны авторизованным пользователям для просмотра и поиска, но изменять и удалять их может только автор.

### 2.2. Архитектура

Система разделена на слои:

```text
app/
├── domain/          сущности предметной области
├── repositories/    операции с базой данных
├── services/        бизнес-логика
├── infrastructure/  БД, JWT, bcrypt и Fernet
└── api/             HTTP-эндпоинты и авторизация

frontend/            HTML, CSS и JavaScript
```

Пароли хэшируются с помощью bcrypt. Access-токен создаётся в формате JWT и хранится в HttpOnly cookie. Конфиденциальное содержимое шифруется с помощью Fernet перед сохранением в PostgreSQL. Секреты и ключи загружаются из файла `.env`.

## 3. Разработанная методика оценки защищённости системы

Предлагаемая методика предназначена для последовательной оценки защищённости веб-приложений. Она сочетает анализ архитектуры и исходного кода с проверкой поведения системы во время работы.

### Этап 1. Определение границ и активов системы

На первом этапе необходимо:

1. Определить назначение системы и её пользователей.
2. Составить перечень компонентов приложения.
3. Определить границы доверия между frontend, backend, базой данных и ОС.
4. Определить активы, которые необходимо защищать:
   - учётные записи;
   - пароли;
   - JWT и cookie;
   - конфиденциальные записи;
   - база данных;
   - ключи шифрования;
   - исходный код;
   - доступность веб-сервера.

### Этап 2. Анализ физических устройств и хранения данных

Необходимо определить, где физически размещаются база данных, резервные копии, ключи и журналы приложения.

Проверяются:

- права доступа к файлу базы данных;
- права доступа к файлу `.env`;
- возможность получения несанкционированного доступа к PostgreSQL volume;
- наличие резервного копирования;
- защита резервных копий;
- использование шифрования диска;
- возможность восстановления системы после повреждения данных.

Результатом этапа должен быть перечень рисков нарушения конфиденциальности, целостности и доступности файлов.

### Этап 3. Анализ ОС и программного окружения

Проверяются:

- версия ОС;
- версия Python;
- версии FastAPI, SQLAlchemy, bcrypt, PyJWT, cryptography и других зависимостей;
- запуск приложения от имени пользователя с минимальными правами;
- наличие виртуального окружения;
- отсутствие лишних открытых портов;
- актуальность пакетов и наличие известных уязвимостей.

Для проверки зависимостей могут использоваться `pip-audit`, `safety` или встроенные средства управления зависимостями.

### Этап 4. Анализ исходного кода

Исходный код анализируется с целью обнаружения:

- SQL-инъекций;
- XSS и небезопасной вставки пользовательского ввода;
- отсутствия проверки авторизации;
- ошибок проверки владельца записи;
- небезопасной обработки исключений;
- утечки секретов в коде;
- использования слабых алгоритмов хэширования и шифрования;
- уязвимостей десериализации;
- ошибок управления сессиями и токенами.

Для автоматической проверки могут использоваться Bandit, Semgrep и аналогичные статические анализаторы.

### Этап 5. Анализ компонентов и их взаимодействия

Для каждого компонента необходимо определить:

1. какие данные он принимает;
2. какие данные возвращает;
3. какие права ему нужны;
4. с какими компонентами он взаимодействует;
5. какие последствия вызовет его компрометация.

Отдельно проверяется, не может ли frontend напрямую обойти бизнес-логику, обращаясь к API. Проверяется, что API самостоятельно контролирует владельца записи и не доверяет идентификаторам, переданным клиентом.

### Этап 6. Сетевой анализ

Проверяются:

- используемые порты и протоколы;
- наличие HTTPS;
- настройки CORS;
- флаги cookie;
- корректность обработки HTTP-методов;
- раскрытие служебной информации в ответах;
- защита от перебора паролей и большого числа запросов;
- возможность доступа к служебным маршрутам.

Для анализа могут использоваться OWASP ZAP, Burp Suite, Nmap и инструменты разработчика браузера. Сканирование должно выполняться только в разрешённой тестовой среде.

### Этап 7. Анализ конфиденциальности, целостности и доступности

Для каждого вида данных оцениваются:

- конфиденциальность — кто может прочитать данные;
- целостность — кто может изменить или удалить данные;
- доступность — можно ли получить данные и воспользоваться системой после сбоя или атаки.

Дополнительно анализируются неожиданные результаты: доступ к чужой записи, чтение данных без входа, повторное использование токена после выхода, повреждение базы данных, раскрытие содержимого через ошибки и выполнение нежелательных действий через frontend.

### Этап 8. Формирование отчёта и плана улучшений

По результатам всех этапов для каждой найденной проблемы указываются:

- компонент;
- описание уязвимости;
- нарушаемое свойство безопасности;
- вероятность эксплуатации;
- возможный ущерб;
- уровень риска;
- рекомендуемая мера защиты.

## 4. Анализ защищённости предоставленной системы по разработанной методике

### 4.1. Физические устройства и хранение данных

Приложение использует PostgreSQL, развёрнутый в Docker-контейнере. Защита данных зависит от настроек контейнера, Docker volume, сетевого доступа к PostgreSQL и прав пользователя базы данных.

Пароли в базе представлены bcrypt-хэшами. Конфиденциальное содержимое записей шифруется Fernet. Однако ключ Fernet хранится в `.env` на сервере приложения. Поэтому защита базы будет эффективной только при отдельной защите `.env`.

Выявленные риски:

- возможность доступа к PostgreSQL через неправильно опубликованный порт;
- необходимость защиты Docker volume и резервных копий PostgreSQL;
- возможность кражи базы вместе с `.env`;
- отсутствие отдельного описания политики резервного копирования;
- зависимость доступности данных от одного локального файла.

### 4.2. ОС и программное окружение

Приложение запускается в виртуальном окружении Python, что изолирует зависимости проекта от глобальной установки. Конфигурация загружается из `.env`, который исключён из репозитория.

Положительные стороны:

- секреты не должны храниться в исходном коде;
- зависимости перечислены в `requirements.txt`;
- приложение может запускаться без административных прав.

Риски:

- уязвимость в сторонней библиотеке может повлиять на backend;
- зависимости необходимо регулярно обновлять;
- права на каталог проекта не должны разрешать запись всем пользователям ОС;
- запуск development-сервера во внешней сети небезопасен.

### 4.3. Исходный код и компоненты

SQLAlchemy используется вместо ручной конкатенации SQL-запросов, поэтому риск классической SQL-инъекции снижен. Вводимые данные выводятся через HTML-экранирование в frontend.

Проверка владельца выполняется на backend, что важно, поскольку ограничения интерфейса нельзя считать механизмом защиты. Конфиденциальные данные фильтруются по идентификатору пользователя из проверенного JWT.

Потенциальные проблемы:

- в текущей реализации отсутствует rate limiting;
- список отозванных JWT хранится в памяти и теряется при перезапуске;
- обработка cookie требует CSRF-защиты в production-сценарии;
- подробные сообщения ошибок должны контролироваться, чтобы не раскрывать внутренние сведения;
- при большом числе конфиденциальных записей поиск расходует память backend.

### 4.4. Взаимодействие компонентов

Поток защищённого запроса выглядит следующим образом:

```text
Браузер → API → проверка cookie/JWT → сервис → репозиторий → PostgreSQL-контейнер
                                      ↓
                           Fernet-расшифрование
```

Проверка JWT выполняется до передачи запроса в сервис. Сервис проверяет владельца записи. Репозиторий выполняет операцию с базой. Такое взаимодействие препятствует прямому обходу бизнес-логики через HTTP-запрос.

Основной риск взаимодействия — компрометация backend-процесса. Backend имеет доступ и к базе, и к ключу шифрования, поэтому его компрометация может привести к раскрытию конфиденциальной информации.

### 4.5. Сетевая безопасность

CORS ограничен origins `http://127.0.0.1:8000` и `http://localhost:8000`, что безопаснее wildcard-разрешения. Frontend и API работают на одном локальном сервере.

В локальном режиме используется HTTP. Поэтому при доступе к приложению через недоверенную сеть cookie и запросы могут быть перехвачены. Для production необходим HTTPS и флаг `Secure` для cookie.

Возможные сетевые атаки:

- перебор имени пользователя и пароля;
- перехват незашифрованного HTTP-трафика;
- CSRF-запросы при использовании cookie;
- сканирование маршрутов и служебной информации;
- DoS за счёт большого количества запросов поиска или авторизации.

### 4.6. Конфиденциальность данных

Конфиденциальные данные хранятся в отдельной таблице и шифруются перед записью в БД. Доступ к ним предоставляется только владельцу. Пароли защищены bcrypt и не могут быть расшифрованы.

Поиск конфиденциальных данных выполняется на backend: записи текущего пользователя загружаются из базы, расшифровываются, после чего выполняется поиск в памяти. Это сохраняет возможность поиска, но при большом объёме данных ухудшает производительность.

Главный риск конфиденциальности заключается в том, что процесс приложения обладает ключом шифрования. Поэтому защита зависит от безопасности ОС, `.env`, backend-процесса и резервных копий.

### 4.7. Сводка рисков

| Риск | Свойство | Уровень | Комментарий |
|---|---|---:|---|
| HTTP без TLS | Конфиденциальность | Высокий | Возможен перехват cookie и запросов |
| Cookie без CSRF-защиты | Целостность | Средний | Возможны нежелательные действия от имени пользователя |
| Нет rate limiting | Доступность и конфиденциальность | Средний | Возможен перебор паролей и перегрузка API |
| Секреты и ключи на сервере приложения | Конфиденциальность | Средний | Компрометация backend раскрывает ключ |
| In-memory список отозванных токенов | Целостность | Средний | Отзыв токенов теряется после перезапуска |
| Неправильная защита PostgreSQL и Docker volume | Конфиденциальность и целостность | Средний | Возможен доступ к данным или их изменение |
| Поиск расшифровывает записи в памяти | Доступность | Низкий/средний | Риск роста времени и памяти при больших данных |

## 5. Предложенный комплекс мер по усовершенствованию защищённости предоставленной системы

### 5.1. Меры на уровне ОС и хранения

- запускать приложение от отдельного пользователя без административных прав;
- ограничить права чтения и записи `.env`, Docker-конфигурации, PostgreSQL volume и каталога проекта;
- использовать шифрование диска;
- хранить резервные копии в отдельном защищённом хранилище;
- шифровать резервные копии базы данных;
- не включать `.env` и реальные базы данных в систему контроля версий;
- регулярно проверять зависимости на уязвимости.

### 5.2. Меры на уровне приложения

- заменить in-memory список отозванных токенов на таблицу сессий или Redis;
- добавить ограничение количества попыток входа;
- установить минимальные требования к паролям;
- добавить журналирование регистрации, входов, выходов и отказов в доступе;
- исключить внутренние сведения из production-ответов об ошибках;
- добавить автоматическое истечение и ротацию ключей;
- реализовать резервный механизм восстановления ключей шифрования;
- добавить пагинацию для списков и поиска.

### 5.3. Сетевые меры

- использовать HTTPS;
- установить `Secure`, `HttpOnly` и подходящий `SameSite` для cookie;
- внедрить CSRF-токены;
- оставить в CORS только реальные адреса frontend;
- разместить приложение за reverse proxy;
- закрыть прямой доступ к Uvicorn из внешней сети;
- ограничить размер запросов и время их выполнения;
- применить rate limiting.

### 5.4. Меры контроля качества

- выполнять статический анализ с помощью Bandit и Semgrep;
- выполнять проверку зависимостей через `pip-audit`;
- проводить динамическое сканирование OWASP ZAP в тестовой среде;
- проверять API через Burp Suite или аналогичный прокси;
- проверять маршруты, права доступа и попытки доступа к чужим записям;
- проверять систему на SQL-инъекции, XSS и CSRF;
- проводить повторную оценку после каждого существенного изменения.

## 6. Предложенные рекомендации по безопасному использованию предоставленной системы

1. Не запускать приложение от имени администратора.
2. Не публиковать файл `.env`, ключ Fernet и JWT-секрет.
3. Не передавать `.env`, Docker-конфигурацию и резервные копии PostgreSQL посторонним лицам.
4. Использовать уникальный сложный пароль для каждой учётной записи.
5. Не использовать приложение по обычному HTTP в недоверенной сети.
6. Для внешнего размещения настроить HTTPS и флаг `Secure` для cookie.
7. Не отключать проверку сертификата TLS в production.
8. Регулярно обновлять Python и зависимости проекта.
9. Ограничить доступ к порту приложения межсетевым экраном.
10. Регулярно создавать зашифрованные резервные копии базы данных.
11. Проверять права доступа к конфиденциальным записям после изменений приложения.
12. Не вводить конфиденциальные данные в общедоступные или тестовые среды.
13. Не использовать один ключ шифрования одновременно в разных независимых системах.
14. После подозрения на компрометацию заменить JWT-секрет и ключ шифрования по процедуре восстановления.
15. Проводить тестирование безопасности только с разрешения владельца системы.

## 7. Вывод

### 7.1. Семантическая составляющая

В ходе работы разработана комплексная методика оценки защищённости программной системы. Методика охватывает физические устройства хранения, операционную систему, программное окружение, исходный код, используемые компоненты, взаимодействие между компонентами, сетевые протоколы и сценарии нарушения конфиденциальности, целостности и доступности.

По этой методике проанализировано предоставленное веб-приложение. Установлено, что система реализует базовые механизмы защиты: bcrypt-хэширование паролей, JWT-аутентификацию, HttpOnly cookie, разграничение доступа по владельцу, CORS с конкретными origins и Fernet-шифрование конфиденциальных данных.

Одновременно выявлены ограничения: отсутствие HTTPS в локальном режиме, отсутствие CSRF-защиты и rate limiting, хранение отозванных токенов в памяти, зависимость от безопасности `.env`, Docker и PostgreSQL, а также загрузка и расшифрование данных в памяти при поиске.

### 7.2. Прагматическая составляющая

Практическим результатом работы являются методика анализа, перечень выявленных рисков, комплекс мер защиты и рекомендации для пользователей и администраторов системы. Предложенные меры позволяют перейти от учебной локальной реализации к более защищённому варианту эксплуатации.

Для промышленного использования в первую очередь необходимо внедрить HTTPS, CSRF-защиту, rate limiting, постоянное хранилище сессий и отозванных токенов, защищённое управление ключами, контроль прав ОС и регулярное автоматизированное сканирование безопасности.

Таким образом, предоставленная система соответствует функциональным требованиям учебного задания, а разработанная методика позволяет системно оценивать её защищённость и планировать дальнейшее совершенствование.
